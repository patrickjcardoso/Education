Por que estudar branches

Por que integrar cedo: 3 semanas separados, 2 dias para juntar

Uma equipe de 6 devs dividiu um sistema de vendas em duas frentes: checkout e catálogo. Cada frente trabalhou numa branch própria por 3 semanas, sem integrar com a main. Na véspera do lançamento, chegou a hora de juntar tudo. Esse cenário tem nome no mercado: "merge hell".

Semanas 1–3

Cada branch acumula dezenas de commits. Os dois times renomeiam a mesma classe Produto de jeitos diferentes.

Dia do merge

87 arquivos em conflito. Ninguém lembra mais por que mudou cada linha.

+2 dias

Lançamento adiado. Aparecem bugs que vêm da junção, não de nenhuma das duas frentes.

A lição: o problema não é ter branches; é ficar tempo demais sem integrar. Quanto mais longa a branch, maior e mais caro o conflito. Nesta aula você aprende a usar branches curtas, resolver conflitos e revisar cada mudança. Na Semana 3, isso vira Integração Contínua.

Branches

Branch: uma linha de trabalho isolada, sem copiar o projeto

Situação Você está no meio do filtro por status (o código ainda não funciona) e chega um bug urgente para corrigir na versão que está no ar. Sem branches, você teria de apagar o trabalho pela metade ou entregar código quebrado junto com a correção. Com branches, você deixa o filtro numa linha separada, volta à main, corrige e depois continua de onde parou.

Como o Git enxerga

Cada commit aponta para o commit anterior (o pai). Uma branch é só uma etiqueta móvel que aponta para o último commit de uma linha de trabalho. Criar uma branch é instantâneo: o Git cria uma etiqueta nova, não copia arquivos.

HEAD é a etiqueta "você está aqui": indica a branch atual. A cada commit, a branch para onde o HEAD aponta avança.

Analogia: o histórico é uma estrada de commits. Uma branch é um desvio onde você trabalha sem atrapalhar quem segue pela estrada principal; depois, o desvio volta a se juntar a ela (merge).

Comandos de branch

ComandoO que faz
git branchLista as branches; * marca a atual.
git switch -c feature/xCria a branch e muda para ela.
git switch mainVolta para a main.
git merge feature/xTraz os commits da feature para a branch atual.
git branch -d feature/xApaga a branch já integrada.
git push -u origin feature/xPublica a branch no GitHub.

Tutoriais antigos usam git checkout. Ele também funciona, mas o git switch (desde o Git 2.23) é mais claro.

Merge

Os dois tipos de merge: avanço rápido ou commit de junção

Situação Ana terminou a busca por id e, enquanto isso, ninguém mexeu na main. Bruno terminou o filtro, mas a main já recebeu a mudança da Ana. O Git junta as duas branches de jeitos diferentes, e entender a diferença ajuda a ler o histórico.

Fast-forward (caso da Ana)

A main não andou desde que a feature foi criada. O Git só avança o ponteiro da main até o último commit da feature. Nenhum commit novo é criado.

antes: A ─ B ← main └─ C ─ D ← feature depois: A ─ B ─ C ─ D ← main, feature

Merge commit, ou 3-way (caso do Bruno)

As duas branches andaram. O Git compara 3 versões (o ancestral comum e as duas pontas) e cria um commit de merge com dois pais.

A ─ B ─ E ──────── M ← main └─ C ─ D ───┘ ← feature
Quando dá conflito? Só no merge 3-way, quando as duas branches mudaram as mesmas linhas do mesmo arquivo (ou uma apagou o que a outra editou). Mudanças em arquivos ou trechos diferentes o Git junta sozinho.

Rebase

      
Rebase: reaplicar seus commits sobre a main atualizada

      
Situação Você criou sua branch há 3 dias e, desde então, a main recebeu 5 commits. Antes de abrir o PR, você quer testar sua feature com o código mais recente e entregar um histórico limpo, sem os commits "wip" e "agora vai". É para isso que serve o rebase.

      

        

          
O que acontece

          
Na sua feature, git rebase main pega os commits que só existem na feature e os recria, um a um, depois do último commit da main. O resultado é um histórico em linha reta, como se você tivesse começado a feature agora.

          
antes:  A ─ B ─ E          ← main
             └─ C ─ D       ← feature
depois: A ─ B ─ E ─ C' ─ D' ← feature

          
Repare no ': C' e D' são commits novos, com hashes diferentes de C e D. O rebase reescreve histórico.

        

        

          
Rebase interativo: arrume antes de abrir o PR

          
git rebase -i HEAD~3 abre um editor com os últimos 3 commits. Troque pick por:

          

            
rewordmuda só a mensagem

            
squashjunta ao commit anterior

            
dropdescarta o commit

          

          
Uso típico: transformar "wip", "wip 2" e "agora vai" em um commit limpo feat: adiciona filtro por status.

        

      

      
Regra de ouro do rebase: nunca faça rebase de commits que já estão numa branch compartilhada (a main ou uma branch que o colega também usa). Use rebase só na sua branch, antes de publicar ou antes do merge.

Comparação

      
Merge ou rebase? Cada um tem o seu momento

      
Situação No seu time, metade prefere o histórico "como aconteceu", com todos os merges; a outra metade quer uma linha reta, fácil de ler. As duas visões estão certas, em momentos diferentes: rebase para atualizar a sua branch, merge para integrar na main.

      

        

          
AspectoMergeRebase

          
HistóricoPreserva tudo como aconteceu, com commits de mergeLinha reta, mais fácil de ler

          
Reescreve commits?NãoSim (hashes novos)

          
Seguro em branch compartilhada?SimNão

          
ConflitosResolve uma vez, no commit de mergePode resolver commit a commit

          
Uso típicoIntegrar uma feature na main (via PR)Atualizar sua feature com a main antes do PR

        

      

      
No GitHub, o botão de merge do PR oferece 3 opções: Create a merge commit, Squash and merge (junta todos os commits do PR em um só) e Rebase and merge. Muitos times usam squash para manter a main limpa: cada PR vira um commit.

Caixa de ferramentas

      
stash, cherry-pick e bisect: três comandos para emergências

      
Cada comando resolve uma situação que todo dev enfrenta. Leia a situação de cada cartão antes do comando.

      

        

          
📦
git stash

          
Situação: você está no meio de uma tarefa e precisa trocar de branch para corrigir um bug, mas não quer commitar código pela metade.

          
Guarda as mudanças não commitadas numa "gaveta" e limpa a pasta.

          
git stash
git switch main
# corrige o bug…
git switch feature/x
git stash pop

        

        

          
🍒
git cherry-pick

          
Situação: uma correção feita na main também precisa ir para a versão 1.0, mas sem levar as outras mudanças da main.

          
Copia um commit específico de outra branch para a atual.

          
git switch release/1.0
git cherry-pick 63fa1c4

        

        

          
🔎
git bisect

          
Situação: algo funcionava na v0.1 e parou de funcionar. Entre as duas versões há 100 commits. Qual quebrou?

          
Busca binária: você marca um commit bom e um ruim, e o Git testa o meio até achar o culpado.

          
git bisect start
git bisect bad
git bisect good v0.1
# teste e responda good/bad
git bisect reset

        

      

      
Com 100 commits entre o bom e o ruim, o bisect encontra o culpado em no máximo 7 testes (2⁷ = 128). Você vai usar os três no laboratório.

Estratégias de branching

      
GitFlow, GitHub Flow e trunk-based: três formas de o time organizar branches

      
Situação Num time de 6 pessoas sem combinado, cada um cria branches com nomes diferentes, algumas duram semanas e ninguém sabe qual é a versão estável. Uma estratégia de branching é esse combinado: quais branches existem, quanto tempo duram e como o código chega à produção.

      

        

          
mais estruturado
GitFlow

          
main ────●──────────●
develop ─●──●──●──●─
feature    └─●─┘
release        └●┘

          
Branches fixas main e develop, mais feature/*, release/* e hotfix/*. Bom para versões numeradas e lançamentos agendados. Pesado para deploy contínuo.

        

        

          
equilíbrio
GitHub Flow

          
main ─●────●────●────●
       └─●─┘  └─●─┘
       feature   feature

          
Só a main é permanente, sempre pronta para deploy. Cada mudança nasce numa branch curta, passa por Pull Request e revisão, e entra na main. É o que usaremos no TaskFlow.

        

        

          
mais ágil
Trunk-based

          
main ─●─●─●─●─●─●─●─●
      └●┘   └●┘
     (horas)

          
Todos integram na main (o "tronco") pelo menos uma vez por dia. Branches duram horas. Exige CI forte e feature flags para esconder o que não está pronto. Usado por times de alta performance.

        

      

      
Não existe estratégia "certa": existe a que combina com a frequência de entrega e a maturidade do time. Em todas, vale a mesma regra: branches curtas integram com menos dor.

      
📖 Para aprofundar:GitHub flow (docs oficiais)trunkbaseddevelopment.comPro Git 3.4 · Fluxos de trabalho

Pull Request

      
Pull Request: como propor uma mudança e pedir revisão

      
Situação Na Aula 01 você fez push direto na main. Funciona sozinho, mas em dupla é arriscado: se o colega enviar um bug direto na main, ninguém vê antes de quebrar. O Pull Request (PR) cria uma parada obrigatória: "revise minha branch e, se estiver ok, junte na main". No GitLab, o mesmo recurso se chama Merge Request.

      

        
1
Branch
git switch -c feature/busca-id

        
2
Commits
Pequenos, no padrão Conventional Commits.

        
3
Push
git push -u origin feature/busca-id

        
4
Abrir PR
Botão Compare & pull request. Título, descrição, revisor.

        
5
Revisão
O colega comenta, pede ajustes ou aprova. Novos commits atualizam o PR.

        
6
Merge
Aprovado: Squash and merge e apagar a branch.

      

      
Depois do merge, todo mundo atualiza a máquina local: git switch main e git pull. Só então crie a próxima branch, sempre a partir da main atualizada.

Code review

      
Como abrir um PR fácil de revisar e revisar o código do colega

      
Situação Um PR com 50 linhas é lido com atenção. Um PR com 1.500 linhas recebe um "LGTM" (looks good to me) em 2 minutos, sem ninguém ter lido de verdade, e o bug passa. Revisão só funciona se o PR for pequeno, bem descrito e se o revisor souber o que procurar.

      

        

          
.github/pull_request_template.md

          

## O que muda
<!-- Uma ou duas frases. -->

## Por quê
<!-- Qual problema resolve? Link da issue, se houver. -->

## Como testar
- [ ] `pytest` passa
- [ ] Testei manualmente em /docs

## Checklist
- [ ] Commits no padrão Conventional Commits
- [ ] README atualizado (se mudou endpoint)
- [ ] Sem senhas, tokens ou arquivos .env

        

        

          
Como revisar o código do colega

          
    
            
  • Rode o código: faça checkout da branch e execute os testes.
    • 
            
  • Comente a mudança, não a pessoa: "esta função pode retornar None", e não "você esqueceu de novo".
    • 
            
  • Explique o porquê e, se puder, sugira o código (botão Add a suggestion).
    • 
            
  • Diferencie o obrigatório do opcional: prefixe com "nit:" sugestões pequenas de estilo.
    • 
            
  • Termine a revisão: Approve, Request changes ou Comment.
    • 
          

          
O template ao lado aparece automaticamente em todo PR novo: ele lembra o autor do que o revisor precisa saber.

Configuração no GitHub ⏱ 5 min

      
Proteja a main para que nada entre sem revisão

      
Situação Às 23h, alguém faz push direto na main: "é só um ajuste rápido". O ajuste tinha um erro de digitação numa rota e a API para de responder. Combinados verbais falham; a proteção de branch faz o GitHub recusar qualquer mudança na main que não venha de um PR aprovado.

      

        

          
Passo a passo (no seu fork)

          
    
            
  1. Abra Settings → Branches e clique em Add classic branch protection rule (ou Settings → Rules → Rulesets, a versão nova).
    2. 
            
  2. Em Branch name pattern, digite main.
    3. 
            
  3. Marque Require a pull request before merging.
    4. 
            
  4. Marque Require approvals e deixe 1.
    5. 
            
  5. Deixe desmarcado Allow force pushes e Allow deletions. Salve.
    6. 
          

        

        

          
Teste a proteção

          
Faça um commit direto na main e tente enviar:

          
git push origin main
remote: error: GH006: Protected branch update failed

          
Ótimo: a regra funciona. Desfaça o commit local com git reset --soft HEAD~1, crie uma branch e faça do jeito certo, com PR.

          
Repositório privado? No plano gratuito, a proteção de branch só funciona em repositório público. O fork do TaskFlow é público, então funciona. Alunos têm GitHub Pro grátis pelo GitHub Student Developer Pack.

Colaboração

      
Fork ou collaborator: dois jeitos de contribuir num repositório

      
Situação Você encontrou um erro de digitação na documentação de um projeto open source e quer corrigir. Você não tem permissão de escrita lá, e nem deveria ter. O fork resolve isso: você cria uma cópia na sua conta, muda o que quiser e envia um PR para o projeto original.

      

        

          
ModeloComo funcionaQuando usar

          
CollaboratorTodos têm permissão de escrita no mesmo repositório e criam branches nele.Time pequeno de confiança. A dupla no TaskFlow.

          
ForkCada pessoa tem uma cópia própria e envia PR do fork para o repositório original.Open source: qualquer um contribui sem acesso de escrita.

        

      

      

        

          
Remotos: origin e upstream

          
origin é o seu repositório no GitHub (o fork). upstream é o original, de onde você fez o fork. Liste com git remote -v.

          
git remote add upstream https://github.com/patrickjcardoso/taskflow.git
git fetch upstream
git merge upstream/main

        

        

          
fetch × pull

          
git fetch baixa os commits novos do remoto sem mexer nos seus arquivos. git pull = fetch + merge na branch atual.

          
Atalho: se o professor atualizar o repositório-modelo, use o botão Sync fork na página do seu fork no GitHub.

Autoestudo · Laboratório ⏱ 1 h

      
Laboratório: conflito, rebase, stash, cherry-pick e bisect

      

        

          
Killercoda · Ubuntu Playground

          

# Parte 1 · preparar
git config --global user.name "Seu Nome"
git config --global user.email "seu@email.com"
git config --global init.defaultBranch main
mkdir lab2 && cd lab2 && git init
printf "linha 1\nversao: base\nlinha 3\n" > app.txt
git add . && git commit -m "chore: versão base"

# Parte 2 · gerar e resolver um conflito
git switch -c feature/a
sed -i 's/versao: base/versao: feature A/' app.txt
git commit -am "feat: versão A"
git switch main
sed -i 's/versao: base/versao: main/' app.txt
git commit -am "feat: versão main"
git merge feature/a        # CONFLICT!
cat app.txt                # veja os marcadores
# edite app.txt (nano app.txt), deixe a linha final e apague os marcadores
git add app.txt && git commit --no-edit

# Parte 3 · rebase deixa a história em linha reta
git switch -c feature/b
echo "doc" > doc.txt && git add . && git commit -m "docs: adiciona doc"
git switch main
echo "x" > x.txt && git add . && git commit -m "chore: adiciona x"
git switch feature/b && git rebase main
git log --graph --oneline --all

# Parte 4 · stash e cherry-pick
echo "rascunho" >> doc.txt && git stash
git switch main && git cherry-pick feature/b
git switch feature/b && git stash pop

# Parte 5 · bisect: ache o commit que quebrou
git switch main && git tag bom
for i in 1 2 3 4 5 6; do echo "passo $i" >> log.txt; [ $i = 4 ] && echo "ERRO" >> log.txt; git add . && git commit -qm "chore: passo $i"; done
git bisect start HEAD bom

Glossário da aula

      
Termos que você precisa dominar

      

        
Branch
Ponteiro móvel para um commit. Representa uma linha de trabalho.

        
HEAD
Indica a branch (ou commit) em que você está agora.

        
Merge
Junta o histórico de uma branch em outra.

        
Fast-forward
Merge sem commit novo: a branch de destino só avança o ponteiro.

        
Merge commit
Commit com dois pais, criado quando as duas branches andaram.

        
Conflito
As duas branches mudaram as mesmas linhas. Uma pessoa precisa decidir o resultado.

        
Rebase
Recria seus commits por cima de outra branch, gerando hashes novos e histórico linear.

        
Squash
Juntar vários commits em um só (no rebase -i ou no merge do PR).

        
Stash
Gaveta temporária para mudanças ainda não commitadas.

        
Cherry-pick
Copia um commit específico para a branch atual.

        
Bisect
Busca binária no histórico para achar o commit que introduziu um erro.

        
Pull Request (PR)
Pedido para revisar e integrar uma branch. No GitLab: Merge Request.

        
Code review
Revisão do código por outra pessoa antes do merge.

        
Fork
Cópia de um repositório na sua conta, independente do original (upstream).
