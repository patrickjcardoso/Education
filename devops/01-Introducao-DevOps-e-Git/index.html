Por que estudar DevOps

Um deploy manual malfeito custou US$ 440 milhões em 45 minutos

Em 1º de agosto de 2012, a Knight Capital, uma das maiores operadoras de ações dos EUA, instalou uma atualização à mão em 8 servidores. Em um deles, a versão nova não foi copiada. Esse servidor ativou um código antigo, esquecido havia anos, que começou a comprar e vender ações sem parar.

Dias antes

Deploy manual, servidor por servidor, sem nenhuma checagem automática de que os 8 ficaram iguais.

09h30

A bolsa abre. O servidor desatualizado dispara milhões de ordens que ninguém pediu.

~10h15

A equipe consegue parar o sistema. Sem monitoramento claro, demorou para achar a causa.

Cultura DevOps

Por que desenvolvimento e operações viviam em conflito

Situação Sexta, 18h. O dev manda um .zip por e-mail: "é só subir, na minha máquina funciona". O operador instala, o sistema cai às 23h e ele passa a madrugada tentando consertar um código que nunca viu. Na segunda, um culpa o outro.

Isso acontecia porque os dois times eram cobrados por metas opostas: um por mudar rápido, o outro por não deixar nada quebrar. Entre eles havia um "muro" por cima do qual o código era jogado.

Desenvolvimento (Dev)

  • É cobrado por entregar mudanças rápido.
  • "Na minha máquina funciona."
  • Entrega e esquece: não vê o sistema em produção.
muro

Operações (Ops)

  • É cobrado por estabilidade: mudança é risco.
  • "Deploy só na sexta à noite, com janela."
  • Recebe código que nunca testou e é acordado quando cai.

O termo DevOps surgiu em 2009, com Patrick Debois e as conferências DevOpsDays, para derrubar esse muro: o mesmo time passa a ser responsável por construir e manter o software funcionando.

Cultura DevOps

DevOps é cultura, processo e ferramenta, nessa ordem

Situação Uma empresa compra a melhor ferramenta de automação do mercado, mas continua com deploys mensais e 5 aprovações para cada mudança. Seis meses depois, nada melhorou. O que faltou?

Definição: DevOps é um conjunto de práticas culturais, de processo e de ferramentas que aproxima desenvolvimento e operações para entregar software com mais frequência, mais qualidade e menos risco. A ferramenta automatiza uma forma de trabalhar; se a forma de trabalhar não muda, a ferramenta não resolve.

DevOps é…

  • Responsabilidade compartilhada pelo software em produção.
  • Mudanças pequenas e frequentes, fáceis de testar e desfazer.
  • Automação de tudo que é repetitivo: build, teste, deploy.
  • Medir o que acontece e aprender com falhas, sem caça a culpados.

DevOps não é…

  • Um cargo isolado que "faz o deploy" pelos outros.
  • Comprar uma ferramenta e manter o mesmo processo.
  • Pular testes para entregar mais rápido.
  • Só para empresas grandes: uma equipe de 3 pessoas também se beneficia.
Sobre o cargo "Engenheiro DevOps": ele existe e costuma cuidar de pipelines e infraestrutura. Mas, se só essa pessoa "faz DevOps", o muro apenas mudou de lugar.

Princípios

CALMS: 5 perguntas para saber se um time pratica DevOps

O modelo CALMS (John Willis e Damon Edwards, ampliado por Jez Humble) funciona como um checklist. Para cada letra, veja a pergunta e um exemplo prático.

C

Culture

O time colabora e aprende com erros, sem buscar culpados?

Na prática: após uma falha, o time escreve o que aconteceu e o que muda no processo.

A

Automation

Tarefas repetitivas são feitas por máquina?

Na prática: os testes rodam sozinhos a cada mudança.

L

Lean

O trabalho flui em lotes pequenos, sem esperas?

Na prática: 10 entregas pequenas por semana, em vez de 1 grande por mês.

M

Measurement

As decisões se baseiam em dados?

Na prática: o time sabe quanto tempo leva do commit à produção.

S

Sharing

Conhecimento e responsabilidade são compartilhados?

Na prática: dev e ops olham o mesmo painel e participam do mesmo plantão.

Repare: só um dos cinco pilares (Automation) é sobre ferramentas. Os outros quatro são sobre pessoas e processos.

Princípios

Os Três Caminhos: fluxo, feedback e aprendizado

Modelo de Gene Kim (livros O Projeto Fênix e Manual de DevOps), também usado no Jornada DevOps da bibliografia. Cada caminho resolve um problema diferente.

1º caminho

Fluxo

Acelerar o caminho do código até o cliente: lotes pequenos, menos esperas, automação, nunca passar defeito adiante.

Problema que resolve: uma correção pronta em 1 hora que leva 3 semanas para chegar ao usuário.

2º caminho

Feedback

Informação rápida no sentido contrário: testes automáticos, monitoramento e alertas avisam o time antes do cliente.

Problema que resolve: descobrir um bug pelas reclamações nas redes sociais.

3º caminho

Aprendizado contínuo

Experimentar, errar com segurança e melhorar sempre. Pós-incidente sem culpados (blameless postmortem).

Problema que resolve: o mesmo erro acontecendo de novo porque ninguém registrou a causa.

Volte ao caso Knight Capital: faltou fluxo (deploy manual), faltou feedback (45 minutos para perceber) e faltou aprendizado (código antigo esquecido no servidor).

O que um sistema de controle de versão faz

Um sistema de controle de versão (VCS) guarda um histórico de cada mudança nos arquivos, com o quê mudou, quem mudou, quando e por quê (a mensagem).

  • Volta a qualquer versão anterior em segundos.
  • Várias pessoas trabalham ao mesmo tempo sem se sobrescrever.
  • Cada versão em produção tem um identificador exato.
  • É a base de tudo que vem depois: CI, CD e infraestrutura como código partem de um repositório.

Analogia: o controle de versão é um "Ctrl+Z com memória infinita" do projeto inteiro, compartilhado com a equipe e com anotação de cada passo.

Controle de versão

Por que o Git é distribuído e o que isso muda no dia a dia

Situação O servidor da empresa saiu do ar por 1 dia. No sistema antigo (centralizado), ninguém conseguiu registrar trabalho e o histórico corria risco. Com Git, cada dev continuou fazendo commits no próprio notebook e sincronizou quando o servidor voltou.

O Git foi criado em 2005 por Linus Torvalds para o código do kernel Linux. Ele é distribuído: cada pessoa tem uma cópia completa do repositório, com todo o histórico.

AspectoCentralizado (ex.: SVN)Distribuído (ex.: Git)
Onde fica o históricoSó no servidor centralEm cada máquina, completo
Trabalhar offlineNão consegue fazer commitCommit, log e branch funcionam offline
Servidor caiuNinguém trabalha; risco de perder históricoQualquer cópia restaura o projeto
Uso hojeSistemas legadosPadrão do mercado (GitHub, GitLab, Bitbucket, Azure DevOps)
Git ≠ GitHub. Git é a ferramenta de versionamento, que roda na sua máquina. GitHub é um serviço online que hospeda repositórios Git e adiciona colaboração (Pull Requests, Issues, Actions).

Configure o Git e faça seu primeiro commit

Antes do primeiro commit, o Git precisa saber quem você é: nome e e-mail vão em cada registro do histórico. Sem isso, o Git recusa o commit ou registra um autor genérico.

terminal · Git Bash, PowerShell ou Killercoda
# 1. Identifique-se (uma vez por computador)
git config --global user.name "Seu Nome"
git config --global user.email "seu@email.com"
git config --global init.defaultBranch main

# 2. Crie um repositório de teste
mkdir aula01 && cd aula01
git init

# 3. Crie um arquivo e registre
echo "# Aula 01 de DevOps" > README.md
git status
git add README.md
git commit -m "docs: cria README inicial"

# 4. Confira o histórico
git log --oneline

Observe e responda (clique para ver o gabarito)

Cada commit guarda o autor. Use o mesmo e-mail da sua conta do GitHub para que os commits apareçam vinculados ao seu perfil.
Antes: README.md em Untracked files (o Git não o acompanha). Depois: em Changes to be committed, ou seja, na staging area.
É o início do hash SHA-1 do commit: um identificador único calculado a partir do conteúdo. Com ele você referencia aquele commit em qualquer comando.
No Windows, use o Git Bash (instalado junto com o Git) para que os comandos funcionem exatamente como no slide.

Git · Boas práticas

Como escrever mensagens de commit que explicam a mudança

Situação São 3h da manhã e a API do TaskFlow começou a devolver erro no cadastro de tarefas. Você abre o histórico para descobrir qual mudança causou o problema. Qual dos dois históricos abaixo ajuda?

Histórico A

a1f3c9e ajustes 7b2d410 update e94c07a wip 3c5f2b1 agora vai d0a8e66 mudanças gerais

Nenhuma mensagem diz o que mudou. Você vai precisar abrir commit por commit.

Histórico B

a1f3c9e docs: explica como rodar os testes 7b2d410 fix(tasks): rejeita título vazio no cadastro e94c07a feat(tasks): adiciona filtro por status 3c5f2b1 test: cobre exclusão de tarefa d0a8e66 chore: atualiza fastapi para 0.115

Em segundos você suspeita do 7b2d410: ele mexeu no cadastro.

O padrão Conventional Commits

A primeira linha segue o formato tipo(escopo): descrição:

  • tipo: a natureza da mudança (feat, fix, docs… veja ao lado).
  • escopo (opcional): a parte do sistema afetada, entre parênteses.
  • descrição: o que a mudança faz, em até ~72 caracteres, sem ponto final.

Ferramentas de CI leem esse padrão para gerar a lista de mudanças de cada versão automaticamente.

Tipos mais usados

feat nova funcionalidade
fix correção de bug
docs só documentação
test adiciona ou corrige testes
refactor melhora código sem mudar comportamento
style formatação, sem mudar lógica
chore tarefas gerais (dependências, configs)
ci pipeline de integração contínua
Regra de ouro: commits pequenos e atômicos. Um commit = uma mudança com um único objetivo. Assim a mensagem fica fácil de escrever e o commit fica fácil de desfazer.

Desfazendo erros: qual comando usar em cada situação

Situação Você enviou ao GitHub um commit que quebrou o cálculo de prazo, e seu colega já baixou esse commit. Se você "apagar" o commit da sua máquina, o histórico dos dois fica diferente e o próximo push vira uma bagunça. A saída certa é registrar um novo commit que desfaz o erro.

A pergunta que decide o comando é: o erro já foi compartilhado?

SituaçãoComandoO que aconteceSeguro?
Apaguei ou estraguei um arquivo e ainda não fiz commitgit restore arquivoVolta o arquivo para a versão do último commit.Perde a edição local
Fiz git add de algo que não queriagit restore --staged arquivoTira da staging; a edição continua na pasta.Sim

Do local ao remoto

Publicar o repositório no GitHub e autenticar com token

Situação Seu notebook queimou na véspera da entrega. Se o projeto só existia nele, todo o histórico se foi. Com uma cópia no GitHub (o repositório remoto), basta um git clone em outra máquina. O remoto também é o ponto de encontro da equipe.

Passo a passo

  1. No GitHub, clique em New repository. Dê um nome e não marque "Add a README" (você já tem um local).
  2. Copie a URL HTTPS do repositório, no formato https://github.com/usuario/repo.git
  3. Conecte o local ao remoto: git remote add origin <url>
  4. Envie: git push -u origin main (o -u só na primeira vez).
  5. Atualize a página do GitHub: seus commits estão lá.

Erro comum: a senha não funciona

remote: Invalid username or token. Password authentication is not supported for Git operations.

O GitHub não aceita a senha da conta no terminal. Use uma destas opções:

  • Personal Access Token (PAT): crie em Settings → Developer settings → Personal access tokens, com escopo repo, e cole no lugar da senha.
  • VS Code ou GitHub Desktop: fazem login pelo navegador.
  • Chave SSH: configure uma vez e não digita mais nada.
No Killercoda, use o PAT. Nunca coloque o token dentro de arquivos do repositório.

Glossário da aula

Termos que você precisa dominar

DevOps
Práticas de cultura, processo e ferramentas que aproximam desenvolvimento e operações para entregar software com frequência e qualidade.
CALMS
Modelo de 5 pilares: Culture, Automation, Lean, Measurement, Sharing.
Três Caminhos
Fluxo (do dev ao cliente), Feedback (de volta ao dev) e Aprendizado contínuo.
Métricas DORA
Frequência de deploy, lead time de mudanças, taxa de falha de mudanças e tempo de recuperação.
Deploy
Colocar uma versão do software em funcionamento num ambiente (ex.: produção).
VCS
Sistema de controle de versão: registra o histórico de mudanças dos arquivos.
Repositório
Pasta do projeto mais o histórico completo, guardado em .git.
Working directory
Os arquivos da pasta, como estão agora, incluindo mudanças não registradas.
Staging area
Área de preparação: o que vai entrar no próximo commit (git add).
Commit
Registro de um conjunto de mudanças, com autor, data, mensagem e um hash único.
Hash (SHA-1)
Identificador único de um commit, calculado a partir do conteúdo. Ex.: a1f3c9e.
Remoto (origin)
Cópia do repositório em outro lugar, como o GitHub. push envia, pull traz.
Tag
Nome fixo apontando para um commit, usado para marcar versões (ex.: v0.1).
.gitignore
Lista de arquivos e pastas que o Git deve ignorar (ex.: .venv/, .env).
