Gancho do mundo real

15 minutos fora do ar, toda vez que sai uma versão

Um e-commerce típico sem entrega contínua faz deploy assim: avisa os clientes, para o servidor, copia os arquivos, instala dependências e liga de novo. Agora some dois problemas comuns:

"Funciona no dev, quebra em produção"

O dev usa Python 3.12; o servidor tem 3.9. Uma sintaxe nova faz a API cair logo depois do deploy. Ninguém percebe até os pedidos pararem.

Deploy = parada

Cada versão nova tira o site do ar por 15 minutos. Por isso o time junta mudanças e faz deploy raro, o que deixa cada deploy maior e mais arriscado.

Container resolve o primeiro

A versão do Python, as bibliotecas e o código vão juntos numa imagem. O que foi testado na CI é exatamente o que roda em produção.

Orquestração resolve o segundo

O Kubernetes troca as cópias da aplicação uma de cada vez, só manda tráfego para quem está saudável e volta à versão anterior com um comando.

Entrega contínua

Entrega contínua × implantação contínua

As duas são chamadas de "CD". A diferença está no último passo: quem decide colocar em produção.

Integração contínuacommit→build→testes
Entrega contínuacommit→build→testes→homologação→👤 aprovação→produção
Implantação contínuacommit→build→testes→homologação→⚙ automático→produção

Entrega contínua (Continuous Delivery)

Toda versão que passa no pipeline está pronta para produção. Uma pessoa decide quando publicar, com um clique. Termo popularizado por Jez Humble e David Farley no livro Continuous Delivery (2010).

Implantação contínua (Continuous Deployment)

Toda versão que passa no pipeline vai para produção sozinha, sem aprovação manual. Exige testes muito confiáveis e monitoramento (Semana 6).

Docker

Por que containers?

Um container é um processo isolado que leva junto tudo o que precisa para rodar: sistema base, linguagem, bibliotecas e código. Ele usa o kernel do sistema hospedeiro, por isso é leve e sobe em segundos.

AspectoMáquina virtualContainer
O que isolaUm sistema operacional inteiro, com kernel próprioSó o processo, compartilhando o kernel
Tamanho típicoGigabytesDezenas a centenas de megabytes
Tempo para subirMinutosSegundos
Quantos por servidorPoucosDezenas ou centenas
Uso típicoIsolar sistemas diferentes (ex.: Windows num Linux)Empacotar e escalar aplicações

A analogia do contêiner de navio

Antes dos contêineres padronizados, cada carga era embarcada de um jeito. Com a caixa de tamanho padrão, qualquer navio, trem ou caminhão carrega qualquer carga.

O container de software faz o mesmo: o servidor não precisa saber se dentro há Python, Java ou Node. Ele só sabe rodar containers.

Contrato do ambiente: a imagem testada na CI é a mesma que vai para produção. Acabou a diferença de versão entre a máquina do dev e o servidor.

Docker · Boas práticas

      
Imagens enxutas, seguras e rastreáveis

      

        
🪶
Base pequena
Prefira variantes -slim ou -alpine. Menos pacotes = imagem menor, download mais rápido e menos vulnerabilidades.

        
🧱
Multi-stage
Um estágio instala e compila; a imagem final copia só o resultado. Ferramentas de build não vão para produção.

        
👤
Usuário sem privilégio
Rode como usuário comum (USER appuser), não como root. Se alguém invadir o container, terá menos poder.

        
🏷️
Tag versionada, nunca latest
latest muda sem aviso: você não sabe qual código está rodando nem consegue voltar. Use a versão: taskflow:v0.4.

        
🔐
Sem segredos na imagem
Senhas e tokens entram no container por variáveis de ambiente ou secrets do orquestrador, nunca dentro do Dockerfile.

        
🙈
.dockerignore
Evita copiar .git, .venv e arquivos locais. Imagem menor e sem vazar o que não deve.

      

    

  


  
  

    

      
Implantação automatizada ⏱ 15 min

      
Publique a imagem automaticamente a cada versão

      

        

          
.github/workflows/cd.yml

          

name: CD

on:
  push:
    tags: ["v*"]          # roda quando você cria uma tag v…

jobs:
  imagem:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write     # permite publicar no ghcr.io
    steps:
      - name: Baixar o código
        uses: actions/checkout@v4

      - name: Login no GitHub Container Registry
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Gerar nome e tags da imagem
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ghcr.io/${{ github.repository }}
          tags: type=ref,event=tag

      - name: Construir e publicar
        uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}

        

        

          
Como funciona

          
    
            
  1. Você cria a tag: git tag v0.4 e git push --tags.
    2. 
            
  2. O workflow faz login no ghcr.io com o token automático do próprio Actions (GITHUB_TOKEN). Não precisa criar senha.
    3. 
            
  3. O metadata-action monta o nome ghcr.io/usuario/taskflow:v0.4, em minúsculas.
    4. 
            
  4. O build-push-action constrói com o seu Dockerfile e publica.
    5. 
            
  5. A imagem aparece em Packages, no seu perfil. Abra o pacote → Package settings → Change visibility → Public, para o Kubernetes conseguir baixar sem senha.
    6. 
          

          
CI + CD juntos: a CI (Aula 03) roda a cada PR; o CD roda a cada versão marcada. Só crie a tag depois que a main estiver verde.

        

      

    

  


  
  

    

      
Kubernetes

      
O que o Kubernetes resolve

      
Rodar 1 container é fácil. Rodar 30, em 5 servidores, reiniciando os que caem, distribuindo tráfego e trocando de versão sem parar o sistema, não é. O Kubernetes (K8s) é um orquestrador: você descreve o estado desejado e ele trabalha para mantê-lo.

      

        
      

      

        
ObjetoO que é

        
PodMenor unidade do K8s: um ou mais containers que rodam juntos. É descartável: se cai, outro é criado.

        
DeploymentDiz qual imagem usar e quantas réplicas manter. Faz o rolling update e guarda o histórico para rollback.

        
ServiceEndereço fixo que distribui o tráfego entre os Pods saudáveis, mesmo quando eles são trocados.

        
Nó (node)Máquina (física ou virtual) do cluster onde os Pods rodam.

      

    

  


  
  

    

      
Kubernetes · Manifestos

      
Infraestrutura descrita em YAML: Deployment e Service

      

        

          
k8s/deployment.yaml

          

apiVersion: apps/v1
kind: Deployment
metadata:
  name: taskflow
spec:
  replicas: 3                    # quero 3 cópias
  selector:
    matchLabels:
      app: taskflow
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1                # sobe 1 extra por vez
      maxUnavailable: 0          # nunca fica abaixo de 3
  template:
    metadata:
      labels:
        app: taskflow
    spec:
      containers:
        - name: api
          image: ghcr.io/USUARIO/taskflow:v0.4
          ports:
            - containerPort: 8000
          readinessProbe:        # só recebe tráfego se responder
            httpGet:
              path: /tasks
              port: 8000
            initialDelaySeconds: 3
            periodSeconds: 5
          resources:
            requests: {cpu: 50m, memory: 64Mi}
            limits: {cpu: 250m, memory: 128Mi}

        

        

          

            
k8s/service.yaml

            

apiVersion: v1
kind: Service
metadata:
  name: taskflow
spec:
  type: NodePort
  selector:
    app: taskflow        # envia para Pods com este label
  ports:
    - port: 80
      targetPort: 8000   # porta do container
      nodePort: 30080    # porta aberta no nó

          

          

            
O que observar

            
    
              
  • Declarativo: você diz o estado final ("3 réplicas da v0.4"), não os passos.
    • 
              
  • O label app: taskflow liga o Service aos Pods do Deployment.
    • 
              
  • A readinessProbe impede que um Pod com bug receba tráfego.
    • 
              
  • maxUnavailable: 0 garante deploy sem indisponibilidade.
    • 
            

          

        

      

    

  


  
  

    

      
🛠️ Mão na Massa ⏱ 10 min

      
kubectl: aplicar, observar, atualizar e voltar

      

        

          
ComandoO que faz

          
kubectl apply -f k8s/Cria ou atualiza tudo o que está nos arquivos da pasta. Rodar de novo sem mudança não altera nada.

          
kubectl get pods -o wideLista os Pods, o estado (Running, Pending, CrashLoopBackOff) e em qual nó estão.

          
kubectl describe pod <nome>Detalhes e eventos de um Pod. O primeiro lugar para olhar quando algo não sobe.

          
kubectl logs <pod>Saída do container, como o docker logs.

          
kubectl set image deployment/taskflow api=…:v0.5Troca a imagem e dispara o rolling update (ou edite o YAML e rode apply).

          
kubectl rollout status deployment/taskflowAcompanha a troca, Pod a Pod, até terminar.

          
kubectl rollout undo deployment/taskflowVolta para a versão anterior. Rollback em segundos.

          
kubectl delete pod <nome>Apaga um Pod. Repare que o Deployment cria outro na hora: é a autocorreção.

        

      

      
Experimente no laboratório: apague um Pod e rode kubectl get pods -w. Em poucos segundos aparece um novo. Você declarou "quero 3"; o Kubernetes garante 3.

    

  


  
  

    

      
Discussão

      
Quando o Kubernetes é exagero

      
Kubernetes é poderoso e também complexo: exige gente para operar, monitorar e atualizar o cluster. Ferramenta certa é a que resolve o problema com o menor custo.

      

        

          
CenárioOpção mais simplesQuando migrar para Kubernetes

          
Projeto pessoal ou MVP com 1 serviçoPlataforma gerenciada (PaaS), como Render, Railway, Azure App Service ou Google Cloud RunQuando o custo ou as limitações da plataforma começarem a atrapalhar

          
Poucos containers num único servidorDocker Compose (você usa na Semana 6)Quando precisar de vários servidores ou alta disponibilidade

          
Dezenas de serviços, vários times, tráfego variável—Aqui o Kubernetes (gerenciado pela nuvem: EKS, AKS, GKE) costuma compensar

        

      

      
Para a prova: saiba explicar o que o Kubernetes resolve (escala, autocorreção, deploy sem parada, rollback) e citar um caso em que ele não é a melhor escolha.

kubectl rollout status deployment/web

kubectl rollout undo deployment/web
kubectl get pods

# Autocorreção
kubectl delete pod $(kubectl get pods -l app=web -o name | head -1)
kubectl get pods -w         # Ctrl+C para sair

WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

# ---------- Estágio 2: imagem final, só o necessário ----------
FROM python:3.12-slim
WORKDIR /app
COPY --from=build /install /usr/local
COPY app/ ./app/
RUN useradd --create-home appuser
USER appuser
EXPOSE 8000

Glossário da aula

      
Termos que você precisa dominar

      

        
Entrega contínua
Toda versão aprovada no pipeline fica pronta para produção; uma pessoa decide quando publicar.

        
Implantação contínua
Toda versão aprovada no pipeline vai para produção automaticamente.

        
Rolling update
Troca as instâncias aos poucos, sem parar o serviço.

        
Blue-green
Dois ambientes completos; o tráfego é trocado de uma vez para o novo, e o antigo fica de reserva.

        
Canary
A versão nova recebe uma pequena parte do tráfego antes de ser liberada para todos.

        
Rollback
Voltar para a versão anterior.

        
Container
Processo isolado que leva junto tudo o que precisa para rodar, usando o kernel do hospedeiro.

        
Imagem
Pacote imutável a partir do qual containers são criados; identificada por nome e tag.

        
Dockerfile
Arquivo com as instruções para construir uma imagem.

        
Registry
Repositório de imagens (Docker Hub, ghcr.io).

        
Multi-stage build
Dockerfile com vários estágios; a imagem final leva só o necessário.

        
Orquestrador
Sistema que gerencia muitos containers em vários servidores (ex.: Kubernetes).

        
Pod
Menor unidade do Kubernetes: um ou mais containers rodando juntos.

        
Deployment
Objeto que mantém N réplicas de uma imagem e controla atualizações e rollback.

        
Service
Endereço fixo que distribui tráfego entre os Pods saudáveis.

        
readinessProbe
Teste periódico que decide se um Pod está pronto para receber tráfego.
