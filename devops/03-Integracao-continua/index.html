Por que habilitar o Actions no fork?

Por segurança, o GitHub não roda workflows automaticamente em repositórios que vieram de fork. Você precisa autorizar uma vez. Sem isso, o pipeline que vamos criar nunca executa e o checkpoint 3 não passa.

Custo: em repositório público, os minutos do GitHub Actions são gratuitos e ilimitados nos runners padrão. O TaskFlow é público, então não há custo.

"Na minha máquina funciona"

Situação comum em times sem CI: o PR foi revisado e aprovado, mas ninguém rodou os testes. A revisão humana olha o código; ela não executa o código.

Segunda, 11h

Sem CI

Rodar os testes depende de alguém lembrar. O erro aparece horas ou dias depois, longe de quem causou, e fica caro descobrir qual mudança quebrou.

Com CI

Cada push e cada PR dispara os testes num servidor limpo. Em 1 a 2 minutos o PR da Ana estaria vermelho, com o merge bloqueado e o teste exato que falhou.

Integração Contínua

O que é Integração Contínua (CI)

Integração Contínua é a prática de integrar o código de todos na branch principal com frequência (pelo menos uma vez por dia), com cada integração verificada por um build e testes automáticos. A definição é de Martin Fowler, que popularizou o termo em 2000.

1

Repositório único

Todo o código, os testes e a configuração do build ficam versionados no mesmo lugar.

2

Build automático

Um comando (ou um push) constrói e testa tudo. Nada depende de passos manuais.

3

Testes que se verificam

O resultado é binário e automático: passou ou falhou, sem ninguém olhar telas.

4

Integração frequente

Branches curtas, commits pequenos. Exatamente o que vimos na Aula 02.

5

Build rápido

Até cerca de 10 minutos. Se demora 1 hora, as pessoas param de esperar e ignoram o resultado.

6

Build quebrado se conserta já

Main vermelha é prioridade do time. Ninguém empilha mudanças em cima de um build quebrado.

CI não é uma ferramenta. Instalar o Jenkins numa equipe que integra uma vez por mês não é CI. A ferramenta automatiza a verificação; a prática é integrar sempre. Volte ao CALMS: Automation a serviço de Lean e do 2º Caminho (feedback).

Anatomia de um teste: preparar, agir, verificar

tests/test_tasks.py
def test_busca_tarefa_por_id():
    # Arrange (preparar): cria o cenário
    client.post("/tasks", json={"title": "Estudar CI"})

    # Act (agir): executa o que está sendo testado
    resposta = client.get("/tasks/1")

    # Assert (verificar): confere o resultado
    assert resposta.status_code == 200
    assert resposta.json()["title"] == "Estudar CI"


def test_busca_id_inexistente_retorna_404():
    resposta = client.get("/tasks/99")
    assert resposta.status_code == 404

Regras do pytest

  • Arquivos test_*.py e funções test_* são encontrados sozinhos.
  • Um assert falso faz o teste falhar e mostra os valores comparados.
  • Teste um caso de cada vez: o caminho feliz e os de erro (404, dado inválido).
  • Testes não dependem uns dos outros. No TaskFlow, a fixture limpa_banco zera os dados antes de cada teste.
ComandoPara quê
pytestRoda tudo
pytest -vMostra o nome de cada teste
pytest -k buscaSó testes com "busca" no nome
pytest -xPara no primeiro erro
Qualidade automática

Lint e cobertura: duas verificações baratas

🧹

Lint com ruff

Um linter lê o código sem executá-lo e aponta problemas: imports não usados, variáveis indefinidas, imports fora de ordem. O ruff faz isso em milissegundos.

$ ruff check . F401 `os` imported but unused --> tests/test_tasks.py:2:8 Found 1 error. [*] 1 fixable with the `--fix` option. $ ruff check . --fix # corrige o que é seguro
📊

Cobertura com pytest-cov

Cobertura é a porcentagem de linhas do código executadas pelos testes. Linha nunca executada é linha que pode estar quebrada sem ninguém saber.

$ pytest --cov=app --cov-fail-under=70 Name Stmts Miss Cover app/main.py 34 6 82% Required test coverage of 70% reached.
Cuidado: 100% de cobertura não quer dizer zero bugs. Um teste pode executar a linha sem verificar nada. Cobertura mostra o que não está testado; use como alarme, não como meta absoluta.

Crie o pipeline de CI do TaskFlow

      

        

          
.github/workflows/ci.yml

          

name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  testes:
    runs-on: ubuntu-latest
    steps:
      - name: Baixar o código
        uses: actions/checkout@v4

      - name: Instalar Python 3.12
        uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip

      - name: Instalar dependências
        run: pip install -r requirements.txt ruff==0.17.0 pytest-cov==7.1.0

      - name: Lint (ruff)
        run: ruff check .

      - name: Testes com cobertura
        run: pytest --cov=app --cov-fail-under=70

        

        

          
Passo a passo

          
    
            
  1. Crie uma branch: git switch -c ci/pipeline
    2. 
            
  2. Crie as pastas e o arquivo: mkdir -p .github/workflows e cole o conteúdo em ci.yml. A indentação do YAML usa espaços, nunca Tab.
    3. 
            
  3. Rode localmente antes: pip install ruff==0.17.0 pytest-cov==7.1.0, depois ruff check . e pytest --cov=app. Corrija o que o ruff apontar.
    4. 
            
  4. Commit (ci: adiciona pipeline de integração contínua), push e abra o PR.
    5. 
            
  5. No PR, veja a verificação CI / testes rodar. Clique em Details para ver o log de cada step.
    6. 
          

          
Versões fixas: o ==0.17.0 garante que o pipeline usa sempre a mesma versão do ruff. Sem isso, uma versão nova com regras novas pode quebrar o build de um dia para o outro, sem nenhuma mudança no seu código.

Jenkinsfile · o mesmo pipeline

          

pipeline {
  agent any
  stages {
    stage('Build') { steps { sh 'pip install -r requirements.txt ruff pytest-cov' } }
    stage('Lint')  { steps { sh 'ruff check .' } }
    stage('Test')  { steps { sh 'pytest --cov=app --cov-fail-under=70' } }
  }
}

        

        
Qual escolher?
As ideias são as mesmas: evento → etapas → resultado verde ou vermelho. Se o código está no GitHub, o Actions é o caminho mais curto. O Jenkins continua comum em empresas com servidores próprios ou regras rígidas de onde o código pode rodar. Você vai subir um Jenkins no laboratório para comparar.

      

    

  


  
  

    

      
Boas práticas

      
Um pipeline em que o time confia

      

        
⏱️
Rápido
Meta: até 10 minutos. Use cache de dependências (cache: pip) e rode primeiro o que é barato e falha cedo (lint antes dos testes).

        
🔁
Reprodutível
Versões fixas de Python e das ferramentas. O mesmo commit deve dar sempre o mesmo resultado, hoje ou daqui a um mês.

        
🔐
Sem segredos no código
Senhas e tokens vão em Settings → Secrets and variables → Actions e são lidos como ${{ secrets.NOME }}. O log esconde o valor.

      

      

        

          
Testes "flaky": o inimigo da confiança

          
Um teste flaky (instável) passa e falha sem nenhuma mudança no código. Causas comuns: depender da hora atual, da ordem dos testes, de rede externa ou de dados que sobraram de outro teste.

          
O perigo: o time se acostuma a "rodar de novo até passar" e deixa de acreditar no vermelho. Teste flaky se conserta ou se remove, nunca se ignora.

        

        

          
Main vermelha = prioridade do time

          
Se a main quebrou, a primeira tarefa de quem quebrou é consertar ou reverter (git revert, Aula 01). Empilhar novas mudanças em cima de um build vermelho esconde novos erros atrás do antigo.

          
Ligação com DORA: CI reduz a taxa de falha de mudanças e o lead time, duas das 4 métricas da Aula 01.

Glossário da aula

      
Termos que você precisa dominar

      

        
Integração Contínua (CI)
Integrar o código de todos com frequência, verificando cada integração com build e testes automáticos.

        
Pipeline
Sequência automática de etapas (lint, testes, build…) disparada por um evento.

        
Build
Transformar o código-fonte em algo executável e verificado.

        
Workflow
Arquivo YAML em .github/workflows/ que define um pipeline no GitHub Actions.

        
Evento (on)
O que dispara o workflow: push, pull_request, agendamento etc.

        
Job
Conjunto de steps que roda num mesmo runner. Jobs diferentes podem rodar em paralelo.

        
Runner
Máquina virtual limpa que executa o job e é descartada no fim.

        
Step / Action
Step é cada passo do job; action é um step pronto, reutilizável (uses).

        
Status check
Resultado (verde/vermelho) da CI exibido no PR; pode ser obrigatório para o merge.

        
Teste unitário
Testa uma unidade isolada, sem rede nem banco. Rápido e barato.

        
Teste de integração
Testa partes funcionando juntas (ex.: rota + validação + armazenamento).

        
Teste E2E
Testa o sistema inteiro como o usuário usa. Lento e mais frágil.

        
Lint
Análise do código sem executá-lo, em busca de erros e problemas de estilo.

        
Cobertura
Porcentagem do código executada pelos testes.

        
Teste flaky
Teste instável: passa ou falha sem mudança no código.

        
Jenkinsfile
Arquivo que define um pipeline no Jenkins, escrito em Groovy.
